# Instructions for the current branch rebuild

These instructions apply only to the current work: manually reapplying and reviewing the changes from `playground_draft` onto `playground` to produce a more deliberate implementation and commit history. They are not permanent repository policy.

## Porting groups and order

Use the following order as the starting plan, with one focused commit per group. Bring relevant binding tests alongside each group's implementation. Review the draft's final design without replaying intermediate implementations that were later replaced. Deliberate revisions may change dependencies or require adjusting later groups. Shared files may be extended across groups.

## Review and reporting rules

- Treat `playground_draft` as the baseline for review, not an implementation that must be copied exactly. Deliberate revisions may require corresponding changes in later steps.
- For all CodeGen module code brought over or changed during this work, **generate only what has to be specialized, and write everything else as normal code.** Keep type-specific calls, conversions, and binding structure in code generation. When the same algorithm is emitted repeatedly and only its inputs differ, emit those inputs as data and call a shared runtime helper. For example, numeric selection should receive the candidate types for a trie level rather than emit another copy of the selection algorithm; expected-type lists for diagnostics can be compile-time constants passed to ordinary failure-reporting code. Preserve selection rules, resource lifetimes, and necessary specialization when applying this rule.
- When a Lua lookup returns the pushed value's `LuaType` (for example, `RawGet`, `RawGetByHashCode`, or `GetGlobal`), use that return value for subsequent type checks instead of querying the same value again through `Type` or `Is*`. Forward the returned type through lookup helpers when callers need it. Reuse it only while it still describes the value being checked. Match the types the allocation path actually produces rather than mechanically preserving a broader `Is*` predicate: LuaTinker wrappers always use full userdata, so check `.UserData` without also accepting `.LightUserData`.
- For all Lua table or registry accesses brought over or changed during this work, use `RawGetByHashCode` and `RawSetByHashCode` for pointer keys represented as light userdata, such as addresses of private static keys, instead of `PushLightUserData` followed by `RawGet` or `RawSet`. These call `lua_rawgetp` and `lua_rawsetp` directly, avoiding a separate key push. Preserve key identity and stack balance.
- Use public methods for public API access and `using internal` for access to internal methods. Do not use `[Friend]` to bypass ordinary method visibility. Reserve `[Friend]` for tests or specific extraordinary cases where accessing another class's non-public field or member is preferable and less intrusive than relaxing its visibility; explain why such an exception is justified.
- Add cleanup scopes before raising Lua errors only when actual caller-scoped resources must be disposed first. Interpolated arguments passed to the formatting overload of `SetLastError` do not themselves allocate a caller-scoped string; do not wrap such calls in an extra block merely because they use interpolation. Preserve scopes needed for explicitly scoped temporaries, including those created inside interpolated expressions.
- For all tests brought over or changed during this work, focus assertions on LuaTinker's bindings and observable interop behavior. Remove assertions whose only purpose is to validate a bound dependency's implementation or invariants.
  - Keep suitable existing dependency types as binding targets. Removing dependency-behavior assertions does not imply replacing the target with a custom fixture. Review assertions individually and make the smallest relevant change.
  - Preserve meaningful negative binding coverage, including rejected writes to read-only properties. Do not remove such coverage merely because the property belongs to a dependency.
- In the user-facing reply, report changes from the draft baseline, including implementation differences and assertions or scenarios added, removed, or changed, with reasons. Identify a different baseline explicitly if one is used. Distinguish test-scope changes from intentional changes to the binding contract, and report validation results and execution blockers separately.
- Keep this file focused on this rebuild. Briefly record noteworthy departures from `playground_draft` when they affect behavior, ownership, type identity, or assumptions that later porting groups must preserve. Include the reason, implementation status, and consequences for later work. Omit routine review history and minor edits such as inlining, comment cleanup, formatting, or error-message wording.

## Threat model

The threat model is normal Lua/Beef use, including ordinary mistakes and invalid arguments—not deliberate corruption of internal state or adversarial attempts to subvert runtime invariants. Do not add hardening, defensive branches, or extra abstractions solely for intentionally corrupted inputs; implement only the checks needed for normal behavior.

## Noteworthy design changes

### Group 2: Registry-backed metatable validation

Status: implemented in the current rebuild. This replaces the draft's allocation-header ownership and kind tagging, and its reliance on public class globals for internal type identity, with a shared metatable-based validation model. Metatables now establish ownership and type identity together, avoiding parallel allocation tags and mutable global lookups.

- Store registered class metatables in the Lua registry under private per-type keys. Constructors, methods, properties, inheritance, and conversions must retrieve them internally. Public class names remain Lua-facing access points; rebinding a global must not change internal class identity.
- Recognize LuaTinker metatables through private userdata-kind markers before reading any userdata header or payload. Reduce the header to the information needed to locate the payload.
- Relative to the public API before group 2, remove `User2Type.GetTypeDirect`, `GetTypePtr`, `UnsafeGetTypePtr`, and `UnsafeGetObject`. The draft already replaces the first three with family-specific `TryGetTypePtr` overloads; this rebuild also consolidates `UnsafeGetObject` into `GetObject` so extraction consistently validates ownership. These removals have no compatibility shims; downstream callers must migrate.
- Compare actual metatables with the registry metatable for the expected Beef type, following the existing `__parent` relationship for inheritance. Preserve borrowed and unregistered values. Reject userdata without a recognized pointer metatable before interpreting its payload.
  - Unlike the draft, indexer lookup also follows `__parent`. Indexer access uses the normal class conversion rather than requiring an exact generic wrapper type, so derived instances can use base indexers. Preserve this behavior in later indexer changes.
- Keep class registration unique: registering a different Beef type under an already registered Lua class name must not replace or reuse the existing binding. Repeated registration of a type is also rejected; extend its existing registered metatable through the binding APIs.
- Remove public `LuaTinkerState.SetClassName<T>` in favor of internal `TryRegisterClass<T>`, since registration must establish registry identity rather than just record a name. Downstream callers must use `LuaTinker.AddClass<T>`; no compatibility shim is provided. Later groups must not restore name-only registration.
- Rename `EVMTResult.OkNoMetaTable` to `OkUnregisteredType`: accepted userdata has a metatable, while the expected Beef type may be unregistered. Downstream callers must use the new enum member; no compatibility alias is provided.
- Make `CheckMetaTableValidity<T>` strictly validate LuaTinker pointer userdata, matching `EnsureValidMetaTable<T>`. It is not a general value-conversion predicate. Generic `GetValue<T>` uses a separate preliminary filter so ordinary Lua values still reach their translators. Preserve this distinction in later conversion work.
- Adapt later porting groups to this model rather than restoring draft allocation tags or global-based identity. Cover valid instances, inheritance, borrowed and unregistered values, independence from public globals, and ordinary invalid or foreign userdata. Follow the threat model above; exclude deliberate metatable or upvalue corruption.

### Group 3: Shared generators and variadic constructor counting

Status: implemented in the current rebuild. Port the draft's shared invocation and overload generators and final `CodeWriter`, retaining current argument conversion and selection rules until their later groups. Constructor emission uses group 2's registry-backed metatables.

The final organization separates parameter normalization and trie construction from emission. `LuaParameters.bf` owns the parameter records and normalization helpers; `InvocationCode.bf` owns shared invocation and construction emission. `OverloadTrie.bf` contains the trie implementation, matching records, and tree construction; `OverloadCode.bf` retains type classification, traversal, and selected-overload emission. The standalone `Trie.bf` has been removed. Later groups should extend these existing responsibilities rather than introduce parallel parameter or selection models.

- Decode variadic constructor arguments before allocating the constructor wrapper. Both the current pre-refactor implementation and draft counted the newly pushed wrapper as another Lua argument, rejecting valid variadic calls. Preserve counting based only on supplied arguments when groups 9 and 10 change wrapper allocation and ownership.
- Unlike the draft, constructor emission uses each normalized parameter's `DecodedType` through `comptype(...)` for both scalar and tuple arguments, without a separate scalar type-spelling path. Direct and reflected constructors call the same `EmitConstruction` implementation. This simplifies emission without changing conversion rules; retain declared-type decoding for constructor parameters until a later group explicitly changes it.
- Keep the trie internal to `LuaTinker.Handlers`, colocated with overload construction. This replaces the draft's public `LuaTinker.Helpers.Trie<T>` helper; downstream users of that helper must provide their own implementation. It is an overload-generator detail, not a reusable public API.
- Unlike the draft, `DynamicCall.bf` and `DynamicConstructor.bf` delegate overload generation to the shared `EmitOverloads<T>` in `OverloadCode.bf`. This implemented change removes duplicated candidate normalization, trie setup, and dispatch emission. The handlers retain candidate discovery and filtering, generic-analysis guards, runtime setup, and mixin insertion. `DispatchKind` preserves the distinct constructor, static-method, and instance-method branches, including zero-argument handling and fallback errors; binding behavior is unchanged. Later overload diagnostics should extend this shared emitter rather than restore emission in the handlers.
- Omit the draft's `DiagnosticIndex` fields and normalization arguments in group 3: their consumers belong to the richer overload diagnostics deferred to group 5, so the current generators never read them. This does not mean diagnostic indices are unnecessary; restore the distinction between Lua stack positions and user-facing argument indices alongside the diagnostics that consume it in group 5.
- Unlike the draft, represent ordinary, `this`, and variadic parameters through `LuaParameterRole`, with `IsVariadic` derived from the role, and pass `DispatchKind` through overload traversal instead of constructor/static booleans. This removes contradictory generator configurations without changing binding behavior. Later generator ports must preserve these representations, reference mode separately, and the existing selector flag values.
- Rename the draft's `LuaParameterRole.Receiver` to `LuaParameterRole.This` and the associated `receiver` booleans to `hasThisParameter`, matching the explicit Beef `this` parameter and existing `MatchFlags.This` terminology. This naming change is implemented and does not change binding behavior; use these names in later generator ports.
- After review, remove legacy hash preservation and emit trie branches in their explicit insertion order from candidate discovery. This intentionally replaces dictionary-order precedence for overlapping predicates. The first matching branch that successfully dispatches wins; numeric ties, `Object` catch-all branches, and nil-compatible branches have no implicit specificity ranking. Conversion failure after selection does not retry later candidates. Group 5 must extend this explicit ordering rather than rely on hash iteration.
- Accept empty variadic argument lists in reflected constructor and method dispatch and in bound functions and delegates. During code generation, find the first variadic child in the preceding node's ordered children, preferring an exact fixed-arity terminal when no trailing arguments are supplied; bound-call arity excludes the variadic parameter from the required count. This fixes existing rejection of empty lists rather than merely preserving the draft's behavior. Preserve these rules in later argument and ownership ports.

### Group 4: Ref/out arguments deferred

Status: deferred at the user's request; continue with group 5. The final playground Lua scripts in `playground_draft` do not use explicit `ref(holder)` or `out(holder)` hints. They use primitive reference cells such as `ref.int32(0)` and `ref.uint32(0)`, passed directly to SDL and OpenGL calls; those cells remain planned for group 9.

Preserve existing reference binding behavior while deferring group 4's new value-by-ref support and explicit hints. When porting later groups, separate any shared dependencies from the deferred ref/out features rather than bringing those features over implicitly. Reassess dependencies when implementing group 9's reference cells.

### Group 5: Numeric hints and overload diagnostics

Status: implemented in the current rebuild, with the following departures from `playground_draft`.

- Integrate overload failure emission into the shared `EmitOverloads` path rather than the draft's separate handlers, preserving group 3's ordered traversal and empty variadic dispatch. Apply shared failure tracking to all reflected dispatch, including single methods and constructors, with one sorted, deduplicated set of normalized fixed counts and the minimum variadic count driving both arity validation and its expected-count message. Report visible argument counts, excluding implicit instance/class arguments, and omit fixed counts already covered by the variadic range. This keeps selection and diagnostics in one implementation; later argument ports must extend it rather than restore duplicated emission or dictionary-order precedence.
- Move numeric selection into runtime `StackHelper.SelectNumeric` only when multiple distinct numeric types compete, using the generated candidate list's indices for trie branches. Multi-type dispatch calls `SelectNumeric` once and branches on its result, without a separate candidate-matching pass; the selector immediately rejects values that are neither Lua numbers nor recognized argument hints. Generated dispatch calls `SelectNumeric<Types>(lua, stackIndex, diagnosticIndex)`, where `Types` is a tuple of competing types or a single type. The generic entry point specializes candidate records (type plus enum-like classification), the `int32` candidate index, and the single-type call. Tuple selection fills match flags and counts in one runtime pass, filters enums only when multiple enum-like candidates matched, and recomputes the selected index only if filtering leaves one match. Fixed name views are initialized only in the ambiguity branch; selection and error formatting remain shared ordinary code. Match flags retain candidates surviving range checks, int32 preference, and enum tie-breaking; the error helper formats only those candidates directly into the state's existing error string, without a dispatcher string temporary or a fixed-width mask limit. Later ports must preserve the separate stack and visible argument indices, match storage, and error-path lifetime. A single type specializes to a direct `IsNumericArgument` check without arrays or ambiguity state; `(type)` must not be treated as a one-element tuple. Emit numeric choices as an `if` / `else if` chain and put other branches in its final `else`, preserving their relative order and preventing fallback after a numeric match; values matching no numeric candidate can still reach ordinary fallback branches. Emit expected-type lists as compile-time string literals and record failures through runtime `OverloadFailure`, replacing the draft's case tracking and diagnostic switch. This simplifies generated code while preserving numeric preference, enum ambiguity, deepest-argument diagnostics, and scoped error cleanup. Later argument ports must extend these helpers rather than duplicate selection or failure bookkeeping in the generator.
- Group 5 restores `DiagnosticIndex` alongside its diagnostics, preserving the distinction between Lua stack positions and visible argument indices deferred in group 3. Numeric selection now precedes trie traversal; remaining overlapping nonnumeric branches retain insertion-order precedence, and failed conversion does not retry another candidate. Preserve these rules in later argument ports.
- Replace the draft's `PopNumericArgument` API with `PopHinted` overloads in `StackHelpers/Translators/ArgumentHints.bf`, including integer- and floating-backed typed primitives in generated numeric decoding. This provides a common entry point for future hint kinds while keeping hint-aware argument decoding separate from ordinary `Pop` and `GetValue` conversion. Later hint ports must extend `PopHinted` with suitable overloads, update `IsHintableType` to select that decoder, and migrate draft call sites; do not make hints ordinary convertible values. `IsHintableType` currently delegates to the shared `IsNumericType` predicate, but future nonnumeric hints must not expand numeric overload classification. No compatibility alias is provided.
- Move the public `CanRepresentInteger` and `CanRepresentFloating` helpers from `StackHelper` into `LuaTinker.Helpers` in `Helpers/NumericTypes.bf`, alongside `IsNumericType`. Unlike the draft, numeric classification explicitly accepts both integer- and floating-backed typed primitives through their underlying type. These pure checks are shared by ordinary numeric conversion and hint validation; later ports and downstream callers must use the helper namespace rather than restore hint-specific copies. No forwarding aliases are provided.
- Unlike the draft, apply `CanRepresentFloating` to both untyped numeric matching and ordinary floating-point `Pop` conversion. This prevents finite Lua numbers from overflowing to infinity when narrowed to `float`, lets overload selection choose `double` when only it can represent the value, and rejects NaN and infinity consistently with explicit casts. Resolve floating-backed typed primitives to their underlying `float` or `double` for range validation, preserving their numeric conversion support. Direct functions, delegates, variadic arguments, and host conversions must retain the shared conversion check; validating trie selection alone does not cover those paths.
- Trust recognized numeric hint fields supplied by validated cast construction and enum registration. Unlike the draft, omit checks and diagnostic fallbacks solely for deliberate mutation of hint internals, and omit its hint-corruption test, following the threat model. Later hint kinds must be distinguished before decoding their payloads and preserve this assumption about internal fields.

### Group 6: Typed null-pointer argument hints

Status: implemented in the current rebuild. Preserve the draft's `nullptr.int32` exact `int32*` hint and `nullptr.void` universal pointer hint. A universal hint is ambiguous when distinct pointer types compete at the current trie position; plain `nil` retains existing ordered dispatch and conversion behavior.

- Unlike the draft, decode null-pointer hints through the pointer `PopHinted` overload rather than ordinary pointer `Pop`. Extend `IsHintableType` to include pointers without changing numeric classification. Functions, delegates, constructors, methods, and variadic pointer arguments use the shared argument decoder; ordinary `Pop` and host `GetValue` continue to reject hints as values. Later hint and pointer ports must preserve this distinction.
- Determine the distinct pointer types at each trie position during code generation and emit a shared runtime `EnsureUnambiguousNullPointer` check only when multiple types compete. This replaces the draft's emitted match-counting algorithm: only the universal hint can match different pointer types, so runtime candidate arrays and counting are unnecessary. Preserve separate stack and visible argument indices, including constructors and instance methods.
- Keep null hints on the registered argument-hint metatable and distinguish their kind before reading a typed payload. Trust the construction paths, omitting the draft's deliberate hint-corruption checks and tests under the threat model. This group does not introduce group 4's ref/out hints or group 11's nonnull pointer matching and C-string conversions.

### Group 7: Fixed input spans and caller-scoped conversion

Status: implemented in the current rebuild. Fixed `Span<T>` arguments copy dense raw Lua sequences into caller-scoped storage. Unlike the draft, single-target span conversion and `GetSpan!<T>` use ordinary `Pop!<T>` conversions without an element whitelist, including booleans, characters, typed primitives, wrapper-backed values, pointers, `StringView`, `Object`, `LuaTable`, and nested spans. Reject sparse or invalid keys, incompatible elements, and argument hints. When distinct span types compete, retain numeric/`String` element selection rather than generalizing overload matching to every convertible type: other element types cannot be selected from tables. Preserve the draft's nonempty plain-integer `Span<int32>` preference and empty-table ambiguity among eligible candidates. Table arguments remain reserved for span dispatch, without falling back to `Object` after rejection. `GetSpan!<T>` uses the same popping rules as span arguments: Lua sequences are copied, existing span userdata is borrowed, and validation or conversion failures raise Lua errors inside `PCall` or return an error with the stack restored outside it; reject `GetValue<Span<T>>` at compile time to prevent returning temporary span storage from an ordinary method.

- Unlike the draft, use shared runtime `CheckInputSpan` and `SelectInputSpan` helpers instead of emitting validation and selection bookkeeping at each trie level. Generated dispatch calls `SelectInputSpan<Types>(lua, stackIndex, diagnosticIndex)` with a tuple of competing element types; the generic entry point specializes a static candidate array internally, while selection remains shared ordinary code. Emit selection only when distinct span types compete; a single span target decodes directly after sequence validation. Keep non-throwing element checks limited to the existing numeric/`String` selection rules, without general wrapper, pointer, or nested-span conversion probes. General conversion validates elements through ordinary `Pop`; host `GetSpan` reports decoding errors through its result outside `PCall`, using ordinary Lua error propagation inside protected calls. Numeric strings and numeric-to-string conversion follow ordinary `Pop` for single-target conversion, while overload selection retains the draft's Lua-number/string distinction. Later conversion and overload work must preserve raw sequence ordering, conversion and range checks, separate stack and visible argument indices, and table reservation without fallback after rejection.
- Use the shared ordinary `Pop!<String>` decoder for scalar and span elements rather than special-casing string storage in span conversion. Unlike the draft, copy native Lua strings outside `PCall`, and copy numeric-to-string conversions even inside `PCall` because their temporary Lua strings are no longer rooted after conversion. During `PCall`, borrow actual Lua string data while its source remains rooted; span callers must retain the source table and its string elements throughout use. Copies remain valid throughout the caller's scope after source globals are replaced and Lua garbage collection runs. Userdata wrapping a Beef `String` returns the original object with its existing binding lifetime. Replacing elements in the copied span does not write back to the source sequence; referenced objects and tables retain shared identity. Later string conversion work must preserve this shared ownership policy.
- Dispose table-derived `LuaTable` elements at the end of the caller's scope, including nested span conversions. Their registry references must keep tables alive while the converted span is in use and release them afterward. Cleanup when a later argument decoder raises a Lua error remains deferred as documented in the draft's TODO; this group does not expand that lifetime work.
- Preserve existing borrowed span userdata as both binding arguments and `GetSpan` results, retaining the original storage and its binding lifetime, including overload matching for element types excluded from table-based selection. Unlike the draft, do not apply its unsupported-span AutoTink exclusions; group 8 must preserve general single-target conversion and the narrower overload-selection policy separately. Ref/out and variadic arguments retain their existing roles; this group does not bring over deferred value-by-ref support.
